# Мини-CRM «Объекты и задачи»

Тестовое задание для строительной компании: React + TypeScript + Supabase. Постановщики управляют объектами и задачами, исполнители работают со своими назначениями. Права и переходы статусов обеспечиваются PostgreSQL, а не только интерфейсом.

## Быстрый запуск

Нужен Node.js 22 или новее.

```bash
npm ci
npm run dev
```

Откройте адрес, который напечатает Vite (обычно `http://localhost:5173`). Без переменных окружения доступен **предпросмотр**: вымышленные данные, переключение роли и просмотр карточек. Изменения в нём отключены. Это не замена рабочему Supabase.

## Подключение Supabase

1. Создайте отдельный проект Supabase.
2. В SQL Editor выполните весь файл `supabase/migrations/202611060001_crm.sql` от имени `postgres`. Миграция применяется один раз к новой базе.
3. В настройках Authentication отключите **Allow new users to sign up**. Проверьте, что анонимная авторизация также выключена. Вход по email/password оставьте включённым. Настройка облачного Auth не применяется SQL-миграцией; её нужно выставить отдельно. Для локального Supabase регистрация уже отключена в `supabase/config.toml`.
4. В Authentication → Users создайте вручную три подтверждённые учётные записи:

   | Email | Роль |
   | --- | --- |
   | `manager@example.com` | Постановщик |
   | `executor1@example.com` | Исполнитель |
   | `executor2@example.com` | Исполнитель |

   Задайте отдельные тестовые пароли. Не записывайте пароли в репозиторий. Если выбрали другие email, замените их в `supabase/seed.sql`.
5. Выполните `supabase/seed.sql` в SQL Editor. Он создаст профили, 3 объекта и 5 задач во всех пяти статусах. Переходы и история создаются тем же механизмом, что используется приложением. Seed рассчитан на однократный запуск и откатывается целиком при ошибке.
6. Скопируйте `.env.example` в `.env.local` и заполните:

   ```dotenv
   VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_OR_ANON_KEY
   ```

   Здесь допустим **только публичный publishable/anon key**. `service_role`, `sb_secret_…` и пароль базы приложению не нужны. Все переменные `VITE_` попадают в клиентскую сборку.
7. Перезапустите `npm run dev`. Теперь вместо предпросмотра будет экран входа.

Дополнительные пользователи создаются через Auth; затем администратор добавляет строку `profiles` с их UUID, именем и ролью. Роль не берётся из пользовательских metadata и не меняется через клиентский API.

## Команды

```bash
npm run dev      # разработка
npm run build    # TypeScript + production-сборка в dist/
npm run preview  # локальный просмотр production-сборки
npm test         # проверки реальной SQL-миграции через PGlite
```

Тесты используют изолированный PostgreSQL в WebAssembly, без облака и без Docker. Они создают минимальную совместимую оболочку `auth.users`/`auth.uid()` и выполняют запросы от ролей `authenticated` и `anon`. Они не заменяют проверку Supabase Auth и PostgREST после подключения облака.

## Развёртывание

Приложение — статическая SPA. Можно использовать Vercel, Netlify или свой сервер:

- Build command: `npm run build`.
- Output directory: `dist`.
- Версия Node.js: 22+.
- До сборки добавьте две публичные переменные окружения из примера.
- После изменения переменных пересоберите приложение.
- Добавьте адрес приложения в Site URL настроек Supabase Auth.

Навигация использует hash-маршруты (`#/projects`, `#/task/<uuid>`), поэтому специальные rewrite-правила не нужны. Для GitHub создайте пустой репозиторий и загрузите исходники, исключив `.env.local`, `node_modules` и `dist` согласно `.gitignore`.

## Защита данных

- RLS скрывает от исполнителя чужие задачи, объекты без его задач и чужую историю.
- Колонковые права разрешают постановщику менять только обычные поля задачи; `status`, `author_id`, даты и признак удаления закрыты для прямой записи.
- `transition_task` проверяет текущего пользователя, назначение, роль, ожидаемый старый статус, разрешённый переход и комментарий. Строка блокируется на время операции; новый статус и история сохраняются в одной транзакции.
- История создаётся базой. Через API нет прав на её вставку, изменение или удаление.
- Удаление мягкое: записи скрываются, история сохраняется. Удалить объект/задачу через RPC может только постановщик.
- `SECURITY DEFINER`-функции используют пустой `search_path`, явные имена схем и ограниченные права вызова.

Подробнее — в `docs/architecture.md`. Подход опирается на официальные руководства Supabase: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [функции базы](https://supabase.com/docs/guides/database/functions), [вход по паролю](https://supabase.com/docs/reference/javascript/auth-signinwithpassword).

## Состояние сдачи

Исходники подготовлены без подключения к облачному Supabase по запросу заказчика. До остановки проверок были выполнены production-сборка и 36 SQL-тестов. Последующие изменения, включая рефакторинг на FSD, и итоговый комплект повторно не проверялись по просьбе заказчика. Визуальная проверка в браузере не выполнена.

Публикация приложения, создание GitHub-репозитория, облачных пользователей и проверка облачного окружения остаются за владельцем проекта. Готового публичного URL и рабочих облачных доступов в этом комплекте нет.
